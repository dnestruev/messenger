# Звонки 3 — настройка и проверка Android ↔ iPhone

## Что изменено

- WebRTC-сигнализация (`offer`, `answer`, `ICE`) по-прежнему идёт через зашифрованные сообщения Supabase Realtime.
- SDP отправляется сразу после `setLocalDescription()`, а ICE-кандидаты передаются отдельно (Trickle ICE).
- При `ICE failed` или продолжительном `disconnected` вызывающий инициирует ICE restart, а принимающий запрашивает его через зашифрованную сигнализацию.
- В диагностике есть типы ICE-кандидатов (host/srflx/relay) и выбранный маршрут без IP-адресов.
- Появился модуль `js/calls.js` для ICE и серверная Edge Function `supabase/functions/turn-credentials/index.ts` для временных TURN credentials.

**Важно:** GitHub Pages не может сам быть TURN-сервером. Код подготовлен к TURN, но пока не развернут работающий TURN, звонки через некоторые мобильные сети и VPN будут по-прежнему не проходить.

## Как включить TURN

Нужен свой сервер **coturn** либо совместимый TURN-сервис, поддерживающий механизм shared-secret (TURN REST API). Для обычного coturn включаются `use-auth-secret` и секрет `static-auth-secret`. Секрет должен совпадать с `TURN_SHARED_SECRET` в Supabase.

1. Разверните TURN-сервис с публичным адресом. Рекомендуются маршруты UDP и TCP на 3478, TURN/TLS на 5349 (или TCP 443 при наличии отдельного доступного адреса). Настройте сертификат для `turns:` и открытые relay-порты согласно конфигурации coturn.
2. В **Supabase → Edge Functions → Secrets** задайте:
   - `TURN_SHARED_SECRET`: длинный случайный секрет (тот же, что у coturn);
   - `TURN_URLS`: например, `turn:turn.example.org:3478?transport=udp,turn:turn.example.org:3478?transport=tcp,turns:turn.example.org:5349?transport=tcp`.
3. Разверните Edge Function из папки `supabase/functions/turn-credentials`. Для ручной проверки JWT она развёртывается с `--no-verify-jwt`; внутри функция сама проверяет `Authorization: Bearer ...` через Supabase Auth. Пример команды:

   ```bash
   supabase functions deploy turn-credentials --project-ref YOUR_PROJECT_REF --no-verify-jwt
   ```

4. На обоих телефонах выйдите из старой версии сайта и обновите его, чтобы загрузился `main.js` версии `20261110163000`.

**Не записывайте `TURN_SHARED_SECRET` в `config.js`, коммиты, README или переписку.** Только Supabase Edge Function Secrets и защищённая конфигурация сервера coturn. Само приложение получает временные данные для каждого нового звонка. Развёртывание кода Edge Function в GitHub само по себе **не означает**, что функция запущена в Supabase.

## Как проверить

1. Сначала сделайте голосовой звонок Android Chrome ↔ iPhone Safari через одну сеть Wi-Fi.
2. Повторите на мобильных сетях, затем с включённым VPN.
3. Если звонок не проходит, откройте диагностику обоих устройств и посмотрите:
   - `TURN: подключён в браузере` — временные данные от Edge Function получены (не гарантия доступности самого сервера);
   - `Свои типы: relay:N` — удалось получить relay-кандидатов (N > 0);
   - `Маршрут: relay/... → ...` — WebRTC реально выбрал TURN-маршрут;
   - `ICE restart` — была попытка восстановить соединение.
4. Если TURN указан, но `relay:0` — проверяйте сертификат, DNS, порты, shared-secret, срок времени на телефонах и сетевые ограничения.
5. Если есть `relay`, но `ICE failed` — проверяйте доступность relay-портов, соединение coturn и соответствие версий кода на телефонах.

## Что ещё не проверено

Здесь выполнена только проверка синтаксиса JavaScript и структуры кода. Живые звонки между двумя телефонами, доступность TURN и работа Edge Function ещё **не тестировались**. Смена сети, длительные звонки и одновременные звонки с разных устройств требуют отдельных испытаний.

### Безопасность

TURN передаёт сетевые пакеты, но не должен иметь доступ к содержимому аудио и видео: WebRTC использует DTLS-SRTP. Секрет выдачи TURN credentials остаётся на сервере. Не публикуйте в логах SDP и полные ICE-кандидаты: в них могут содержаться сетевые адреса устройств.
